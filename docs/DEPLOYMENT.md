# راهنمای استقرار AVELORA

> وضعیت: راهنمای آماده‌سازی است؛ این سند به معنی انتخاب میزبان یا تأیید انتشار عمومی نیست.

## معماری

یک سرویس Node.js/Express کل این مسیرها را ارائه می‌کند:
- فروشگاه از `frontend/`
- پنل مدیریت از `admin/`
- API از `/api/*`
- تصاویر از `/uploads/*`

برای استقرار به یک سرویس Node.js، یک PostgreSQL پایدار و یک volume یا object storage دائمی برای تصاویر نیاز است. تا وقتی rate limiter به storage مشترک منتقل نشده، فقط یک نمونه backend اجرا شود.

## متغیرهای محیطی

مقادیر زیر را فقط در پنل محرمانه میزبان تنظیم کنید؛ هیچ‌کدام را در GitHub، کد، فایل قابل‌اشتراک یا پیام قرار ندهید.

| متغیر | مقدار/قاعده |
|---|---|
| `NODE_ENV` | `production` |
| `PORT` | پورت تزریق‌شده توسط میزبان؛ در صورت نیاز میزبان خودش آن را تعیین می‌کند |
| `DATABASE_URL` | اتصال PostgreSQL میزبان؛ اگر ارائه‌دهنده TLS می‌خواهد، پارامتر TLS مستند خودش را اعمال کنید |
| `ADMIN_API_KEY` | راز تصادفی حداقل ۳۲ بایت؛ برای نمونه محلی می‌توان با `openssl rand -hex 32` ساخت |
| `PUBLIC_BASE_URL` | آدرس نهایی عمومی با `https://` |
| `TRUST_PROXY` | تعداد hop یا IP/CIDR دقیق پروکسی‌های مورد اعتماد؛ `1` فقط برای دقیقاً یک hop مورد اعتماد |
| `ZARINPAL_ENABLED` | `false` تا تکمیل دامنه و آزمون sandbox/callback |
| `ZARINPAL_MODE` | `sandbox` تا زمان تأیید جداگانه پرداخت واقعی |

سرور در production بدون `DATABASE_URL`، `PUBLIC_BASE_URL` معتبر HTTPS، کلید مدیریت قوی و `TRUST_PROXY` صریح راه‌اندازی نمی‌شود.

**هشدار پروکسی:** فقط وقتی مقدار `TRUST_PROXY=1` را تنظیم کنید که دقیقاً یک پروکسی مورد اعتماد در مسیر وجود دارد و همان پروکسی هدرهای `X-Forwarded-For` ورودی کاربر را بازنویسی می‌کند. برای چند لایه پروکسی، تعداد hop یا subnetهای مورد اعتماد را از مستندات میزبان تعیین کنید؛ همه هدرهای Forwarded را کورکورانه trusted نکنید.

## فرمان‌های ساخت و اجرا

در ریشه مخزن:
- Build/install: `cd backend && npm ci`
- Start: `cd backend && npm start`
- Health check: `GET /api/health`

برای میزبان‌هایی که working directory دارند، working directory را روی `backend` بگذارید؛ در آن صورت فرمان‌ها به‌ترتیب `npm ci` و `npm start` هستند.

## دیتابیس

### دیتابیس تازه

پس از ساخت یک دیتابیس خالی، از ریشه مخزن اجرا کنید:

```bash
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f database/schema.sql
for migration in 004_customer_membership.sql 005_admin_rbac.sql 006_accounting_error_center.sql 007_product_image_gallery.sql; do
  psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f "database/migrations/$migration"
done
```

این دستورات فقط برای دیتابیس تازه هستند.

### دیتابیس موجود

1. از PostgreSQL پشتیبان تهیه کنید.
2. بازیابی پشتیبان را در یک دیتابیس جداگانه امتحان کنید.
3. نسخه مهاجرت‌های قبلاً اعمال‌شده را بررسی کنید.
4. فقط migrationهای مفقود را در زمان انتشار کنترل‌شده اجرا کنید.
5. پس از هر مرحله ساختار و تعداد رکوردها را بررسی کنید.

هرگز دیتابیس عملیاتی را به `minimarkettiyam_test` یا آزمون‌های CI متصل نکنید.

## ذخیره‌سازی تصاویر

برنامه فایل‌ها را در `backend/uploads/` ذخیره می‌کند. در میزبان، یک volume دائمی را دقیقاً به این مسیر متصل کنید یا قبل از انتشار adapter فضای object storage پیاده‌سازی و آزمون کنید. دیسک موقت کانتینر/هاست برای تصاویر واقعی قابل قبول نیست.

نسخه فعلی مخزن GitHub شامل تصاویر واقعی پوشه `backend/uploads/` نیست. تصاویر موجود در گوشی/ZIP باید جداگانه منتقل شوند و URLهای ذخیره‌شده در دیتابیس با فایل‌های مقصد تطبیق داده شوند. پشتیبان تصاویر باید مستقل از میزبان اصلی نگهداری و بازیابی آن آزمایش شود.

## پشتیبان‌گیری و آزمایش بازیابی

اسکریپت‌ها:
- `bash backend/scripts/backup.sh`: تهیه dump سفارشی PostgreSQL و آرشیو `backend/uploads/` همراه checksum.
- `RESTORE_TEST_DATABASE_URL=... bash backend/scripts/verify-backup.sh /path/to/avelora-....tar.gz`: بررسی checksum و آرشیو و بازیابی در دیتابیس جداگانه و خالی.

نمونه اجرا (مقادیر اتصال فقط در محیط امن میزبان یا نشست محلی تنظیم شوند):

```bash
export DATABASE_URL='...'
export BACKUP_DIR="$HOME/avelora-backups"
bash backend/scripts/backup.sh
```

اسکریپت‌ها فایل‌ها را با مجوز محدود می‌سازند؛ connection string را در log یا manifest ذخیره نمی‌کنند. آرشیو و فایل checksum را به فضای خارج از میزبان اصلی منتقل کنید. صرفاً نگهداری بکاپ روی همان هاست، بکاپ خارج از سایت محسوب نمی‌شود.

**آزمون restore:** فقط یک دیتابیس جدید و خالی به `RESTORE_TEST_DATABASE_URL` بدهید. اسکریپت اگر جدول کاربری در مقصد وجود داشته باشد، restore را متوقف می‌کند. دیتابیس اصلی را هرگز به‌عنوان مقصد آزمون استفاده نکنید. اسکریپت archive تصاویر را از نظر checksum و ساختار می‌سنجد؛ پس از بازیابی فایل‌ها باید URLهای تصاویر محصولات نیز به‌صورت دستی/عملیاتی تطبیق داده شوند.

GitHub Actions همین روند را روی PostgreSQL موقت اجرا می‌کند. این CI جایگزین انتقال نسخه پشتیبان به فضای مستقل و آزمون دوره‌ای بازیابی روی زیرساخت واقعی نیست.

## راه‌اندازی حساب مالک

1. مطمئن شوید `ADMIN_API_KEY` قوی و محرمانه در تنظیمات میزبان قرار گرفته است.
2. پس از آماده‌شدن migrationهای 005 تا 007، پنل `/admin/` را باز کنید.
3. در صورت نمایش راه‌اندازی اولیه، حساب مالک را یک‌بار با نام کاربری و رمز قوی بسازید و کلید راه‌اندازی را فقط در همان فرم امن وارد کنید.
4. پس از ساخت مالک، endpoint راه‌اندازی مجدد مالک باید به‌دلیل وجود مالک قبلی رد شود.
5. کلید `ADMIN_API_KEY` را محرمانه نگه دارید؛ آن را با مدیران فرعی به اشتراک نگذارید.

## پرداخت و سفارش

- زرین‌پال و کارت‌به‌کارت را تا تکمیل HTTPS، سیاست‌های فروشگاه و آزمون کنترل‌شده غیرفعال نگه دارید.
- سفارش آزمایشی را فقط در دیتابیس آزمایشی یا محیط staging انجام دهید.
- پرداخت واقعی فقط پس از تأیید مالک، پیکربندی پذیرنده و آزمون sandbox/callback مجاز است.
