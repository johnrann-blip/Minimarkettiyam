# استقرار AVELORA روی cPanel (Node.js Application)

این راهنما برای ساختار فعلی مخزن و برنامه Node.js موجود در cPanel نوشته شده است. مسیر نمونه زیر با ساختار فعلی استقرار AVELORA هماهنگ است:

- ریشه پروژه: `/home/aveloras/avelora`
- ریشه برنامه Node.js: `/home/aveloras/avelora/backend`
- فایل شروع: `src/server.js`
- نسخه Node.js: `22.x`
- فایل تنظیمات محرمانه: `/home/aveloras/avelora/backend/.env`

## ۱) تنظیم برنامه در cPanel

در بخش **Setup Node.js App** تنظیمات برنامه باید چنین باشد:

| گزینه | مقدار |
|---|---|
| Node.js version | نسخه 22 |
| Application mode | Production |
| Application root | `avelora/backend` |
| Application URL | دامنه اصلی `avelorashop.ir` |
| Application startup file | `src/server.js` |

اگر برنامه از قبل با همین مقادیر ساخته شده است، برنامه جدید نسازید و مسیرها را دوباره تغییر ندهید. فقط مطمئن شوید پوشه‌های `frontend` و `admin` در کنار پوشه `backend` و در ریشه پروژه باقی مانده‌اند؛ سرور فایل‌های سایت و پنل را از همان مسیرها ارائه می‌کند.

## ۲) تنظیمات محرمانه محیط

فایل `backend/.env` باید روی خود هاست باقی بماند و هرگز وارد GitHub یا پیام‌رسان نشود. نام متغیرهای موردنیاز:

- `NODE_ENV=production`
- `PORT` فقط مطابق پورتی که cPanel برای برنامه تنظیم می‌کند؛ اگر cPanel آن را تزریق می‌کند، مقدار دستی متعارض تعریف نکنید.
- `DATABASE_URL` اتصال دیتابیس PostgreSQL ساخته‌شده در cPanel
- `ADMIN_API_KEY` یک راز تصادفی و محرمانه با حداقل ۳۲ بایت؛ در production اجباری است و فقط برای ساخت یک‌باره حساب مالک استفاده می‌شود.
- `CLOUDINARY_CLOUD_NAME`، `CLOUDINARY_API_KEY` و `CLOUDINARY_API_SECRET`؛ هر سه در production اجباری‌اند تا تصاویر محصولات پس از Restart یا انتشار مجدد از بین نروند. این مقادیر را فقط در Environment Variables برنامه cPanel تنظیم کنید.

برای اتصال محلی PostgreSQL در cPanel، در صورت پشتیبانی میزبان از IPv4، از `127.0.0.1` به‌جای `localhost` استفاده کنید تا Node.js به‌اشتباه به آدرس IPv6 یعنی `::1` متصل نشود. نام دیتابیس و نام کاربر باید دقیقاً همان نام کامل ساخته‌شده در cPanel باشند. رمز در URL باید URL-encode شده باشد؛ خود رمز را در گزارش‌ها یا چت ارسال نکنید.

پارامتر `sslmode=require` را فقط مطابق الزام واقعی سرویس PostgreSQL هاست نگه دارید. نسخه فعلی سرور این گزینه را به تنظیم TLS اتصال PostgreSQL تبدیل می‌کند. اگر میزبان اتصال بدون TLS می‌خواهد، این پارامتر نباید بی‌دلیل در URL باقی بماند.

## ۳) نصب وابستگی‌ها

پس از فعال‌کردن محیط مجازی‌ای که خود cPanel برای همین برنامه نشان می‌دهد، در ترمینال هاست:

```bash
cd /home/aveloras/avelora/backend
npm ci
```

از `npm install` برای انتشار تکراری استفاده نکنید؛ `npm ci` دقیقاً از lockfile مخزن نصب می‌کند.

## ۴) ساختار دیتابیس و مهاجرت‌ها

**دیتابیس فعلی را حذف یا از نو ایجاد نکنید.** سرور پیش از بازکردن پورت، مهاجرت‌های افزایشی موردنیاز نسخه فعلی را اجرا می‌کند و نام هر مهاجرت موفق را در جدول `app_schema_migrations` ثبت می‌کند. اجرای هم‌زمان چند worker با قفل advisory PostgreSQL هماهنگ می‌شود.

مهاجرت‌های خودکار نسخه فعلی:
- تنظیمات فروشگاه و ستون‌های تکمیلی سفارش
- حساب مشتری و نشست‌ها
- حساب مدیر، نشست و گزارش فعالیت
- درخواست‌ها و کمپین‌های تبلیغاتی
- لایک محصولات و دیدگاه‌های مشتریان

این مهاجرت‌ها برای ساختار دیتابیس فعلی طراحی شده‌اند و جایگزین ساخت جداول پایه فروشگاه نیستند. برای دیتابیس کاملاً تازه، ابتدا یک‌بار `database/schema.sql` را روی دیتابیس خالی وارد کنید؛ سپس برنامه را اجرا کنید تا مهاجرت‌های نسخه را خودش اعمال کند. روی دیتابیس موجود، فایل پایه را دوباره import نکنید.

## ۵) راه‌اندازی اولیه ورود مالک

پس از Restart موفق برنامه:

1. نشانی `https://avelorashop.ir/api/health` باید پاسخ سالم بدهد.
2. نشانی `https://avelorashop.ir/admin/` را باز کنید.
3. اگر پیام «راه‌اندازی اولیه حساب مالک» نمایش داده شد، کلید `ADMIN_API_KEY` را فقط در همان فرم وارد کنید و نام کاربری و رمز قوی مالک را تعیین کنید.
4. پس از ساخت مالک، از صفحه خارج شوید و با همان نام کاربری و رمز وارد شوید. راه‌اندازی اولیه باید فقط یک‌بار قابل انجام باشد.
5. اگر صفحه ورود عادی نمایش داده شد، حساب مالک از قبل وجود دارد؛ دوباره bootstrap نکنید.

کلید راه‌اندازی را با رمز ورود یکی نکنید و آن را در مرورگر عمومی ذخیره نکنید. اگر ساخت مالک خطا داد، چند بار پشت سر هم فرم را ارسال نکنید؛ ابتدا خطای سرور باید بررسی شود.

## ۶) فایل‌های آپلود و ماندگاری

در محیط production، تصاویر محصول در Cloudinary ذخیره می‌شوند؛ بنابراین سه متغیر Cloudinary در بخش Environment Variables برنامه باید کامل و معتبر باشند. نسخه production عمداً بدون ذخیره‌سازی پایدار تصویر راه‌اندازی نمی‌شود. در توسعه محلی، در صورت نبود تنظیم Cloudinary، مسیر `backend/uploads/` استفاده می‌شود. تصاویر واقعی داخل GitHub نگهداری نمی‌شوند.

## ۷) وضعیت پرداخت

پرداخت زرین‌پال و کارت‌به‌کارت تا وقتی اطلاعات واقعی مالک، HTTPS، تنظیمات درگاه و آزمون کنترل‌شده تکمیل نشده‌اند خاموش بمانند. انتشار این نسخه به‌تنهایی به معنی فعال‌کردن دریافت وجه نیست.

## ۸) مرز کارهای لازم از سمت مالک

کد و مهاجرت‌های برنامه را می‌توان از طریق مخزن آماده کرد؛ اما فقط مالک هاست می‌تواند در cPanel مقدارهای محرمانه را تنظیم و برنامه را Restart کند. رمز دیتابیس، کلید مدیریت یا رمز ورود را برای پشتیبانی یا چت ارسال نکنید.

**معیار پایان مرحله استقرار:** پاسخ سالم `/api/health`، بازشدن `/admin/`، ساخت یا ورود موفق حساب مالک، و باقی‌ماندن تصاویر پس از Restart. ورود محصولات و چیدمان فروشگاه بعد از تحویل پنل به مالک انجام می‌شود.
